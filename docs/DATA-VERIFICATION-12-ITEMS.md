## ① p6 月销量是否同一统计窗口

**证据**：p6 原始响应字段实测分布（4,386 条玩具类 SKU）

```
daysWithTrafarets  分布: 0 → 2,370 条 | 28 → 885 | 27 → 224 | 26 → 53 | 23 → 49
daysInPromo        最大 28，分布 0~28
```

**结论**：窗口 = **28 天**。`daysWithTrafarets` 上限就是 28，`daysInPromo` 上限也是 28。
`= 0` 表示该 SKU 在窗口内没投过推广，**不是另一种窗口**。
同一份响应内所有 SKU 共享同一窗口（一次请求 = 一个快照）。

**不能确定的**：窗口的起止日。响应里**没有** `period_from / period_to / date_range` 字段，
所以无法判断是否与 p7（快照日 2026-10-29）对齐 —— 两者可能错开 1 天。

## ② p6 GMV 口径 / 是否含取消退货

**证据**（4,386/4,386 全量成立）：

```
gmvSum == soldSum            4,386 / 4,386   （完全相等，同一指标的两个名字）
avgPrice == gmvSum/soldCount 4,386 / 4,386   （误差 < 0.02）
nullableRedemptionRate       中位 90.3，97.7% 的 SKU < 100
```

**结论**：
- `GMV = Σ 买家实付`，与 `soldCount` 同基数
- **`soldCount` 是「下单口径」不是「成交口径」** —— 依据是结单率中位仅 90.3%，
  97.7% 的 SKU 结单率 < 100%，说明分母里包含未结单（取消/退货）订单
- 推论（**推断，非直采**）：`gmvSum` 同样包含未结单金额

**不能确定的**：Ozon 是否在 `gmvSum` 里对取消订单做了时间归属调整。响应无此字段。

## ③ p7 搜索量窗口 / 与 p6 是否同窗口

**证据**：`keyword_p7.count_28d` 字段名即窗口；原始 jsonl 有 `snap_date = 2026-10-29`。

**结论**：p7 = **28 天**。但 p7 快照日 10-29、p6 采集于 10-30，**两个窗口大概率错开 1 天**。
不能假设完全对齐；跨源比较（如 p7 `count_28d` vs Seerfar `searchVolume`）需注意此偏移。

## ④ P7 增长语义（环比 / 同比 / 平台自定义）

**证据**：原始 jsonl 字段 `dynamicsIn7` / `dynamicsIn28`。
本应用于反推的 `trendForYear` 字段**是空数组（长度 0）**，无历史序列可验证。

与 Seerfar `growth_30d` 对比（560 个可比词）：

| 词 | p7 dyn_28d | Seerfar g30 | 差 |
|---|---|---|---|
| дамплинг | -28.0 | -28.07 | 0.07 |
| сквиши | 15.0 | 17.81 | 2.81 |
| набор сквишей | 41.0 | 52.62 | 11.62 |

仅 **19.5%** 的词差值 < 1 个点。

**结论**：两者高度相关但**不是同一个数**，口径接近（窗口对窗口的变化）但基数或窗口不同。
**到底是环比还是同比，现有数据无法确定。**

**如何定论**：抓同一批词连续两个月的 p7 快照，验证 `dyn_28d == (本期 − 上期) / 上期`。

## ⑤ CR4 口径

**证据**：`final_report.py:85`

```python
srt = sorted(sales, reverse=True)          # 按销量降序，不是按 position
cr4 = sum(srt[:4]) / total * 100           # total = Σ 可匹配 SKU 销量
```

实测校验（词 `сквиш`）：

| 算法 | 结果 |
|---|---|
| 按 position 前 4 ÷ 全量 | 2.6% |
| 按销量前 4 ÷ 前 30 | 37.3% |
| **按销量前 4 ÷ 全量（库里实际值）** | **32.5%** |

**结论**：CR4 = 按销量排序前 4 名 ÷ 该词**可匹配 p6 的** SKU 销量总和。
**分母不是全站市场**，是 108 搜索位里成功关联 p6 的那部分 → 属「可观测搜索位样本」。

## ⑥ SKU 归并（多规格 / 多件装 / 颜色变体）

**证据**（p6 数据 4,386 条）：

```
sku 去重数            4,386
variantId 去重数      4,386
sku == variantId      0 条（0.0%）
一个 variantId 对应多个 sku 的组数：0
```

**结论**：**当前数据没有任何归并信息**。`sku` 与 `variantId` 严格 1:1，
多规格/多件装/颜色变体在库里就是**彼此独立的记录**，没有产品族结构。

**旁证**：商品详情接口（Seerfar `product/detail`）里 `variants` 字段能给出变体数量
（实测某 SKU = 11），说明**平台侧确实有变体族**，只是 p6 拉不到族关系。
另有旁证：`min_seller_price` 在 top10 热位上 49.2% 的 SKU 该值 < 挂牌价 30%，
疑似「合并变体卡片的最低价」—— 这与此结论方向一致，但**未直接证实**。

**要做归并**：需要按标题相似度 + `variantId` 反查 + 商品详情 `variants` 交叉，或走官方 API 的变体接口。

## ⑩ DRR 口径

**证据**：`drr` 是 **p6 后台直采字段**（`what_to_sell/data/v3` 返回体里的 `drr`），
不是推算、不是外部口径。4,386/4,386 条全部有值。

实测分布（玩具类 4,386 条）：

```
drr == 0        : 1,079 条（24.6%）  ← 没投广告，不是缺数据
drr >  0        : 3,307 条，中位 8.77%，P75 15.41%，max 8664%（异常值）
反推 28 天广告花费: 中位 3,137₽，合计 35,952,661₽
```

**定义**：`drr = 广告花费 ÷ GMV（买家实付）`，单位 %。

**已知出入**：后台 DRR 是平台口径的比率，与「实际扣费/账单」不完全对得上
（max 8664% 这类是 GMV 极小导致的除法放大）。

**需要精确到单个商品时**：用 **p8 explainer** 拉它的广告明细，而不是靠 DRR 反推。
p8 每个搜索位直接给：

| 字段 | 实测值示例 |
|---|---|
| `promotionStatus` | 推广中 / 空 |
| `promotionCpcRate` | `46,65 ₽`（CPC 出价） |
| `promotionCpoRate` | 已关闭 |
| `salePromotions` | 是 |

所以：**DRR 用于批量筛（够用），CPC/推广状态用于单品核查（精确）。**
