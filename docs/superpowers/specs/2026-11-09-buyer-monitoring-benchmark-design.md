# Ozon V2 前台采集监控与 12 小时基准测试设计（草案）

> 状态：待用户审核；**本文件不是实施授权**。日期：2026-11-09。
> 现有主分支基线：`05884b6538eddce211b38df71ff26fbee874402b`；归档分支：`archive/pre-v2-2026-11-09`。
> 本设计仅限第一阶段；正式 5 Worker、后台 P6/P7/P8、分析面板和试销决策模型分别设计。

## 1. 意图与业务背景

用户已有 Ozon Buyer/Seller 采集 Demo；后续需支持类目→关键词→SKU→利润研究，以及库存/评论的日度跟踪。目标是最终让同一服务器上的 5 个 Worker 共享队列运行，每日可处理约 100 万条 SKU 库存观测（待性能验证）。当前**先不设计 Worker 最终并发量**，先对买家前台库存代理字段与评论接口做合规、低风险、可重复的 12 小时稳定性测试，得到真实吞吐、数据质量与资源成本依据；后台接口留到下一阶段。

## 2. 已有代码与现实约束

- 可复用：`ozon_buyer/` 的纯解析函数、`collector/adapters/base.py` 的适配器契约、`collector/rate_limit/distributed.py`、`collector/errors.py`、`collector/api.py` 的指标与监控入口，及既有 Prometheus/Grafana 配置。
- **Cookie 供给是硬前置，不是可选项**：`collector/adapters/buyer_snapshot.py` 当前仅允许离线快照，但买家前台 PDP 与搜索接口在无 Cookie 时一律返回 403 + `ozon-antibot` 头，没有 Cookie 供给就没有在线采集。V2 必须把这层显式建模成「预热门 + 池」，而不是当作规避手段排除在外。
- **供给门的边界（允许 / 禁止）**：
  - 允许：CDP 预热获取挑战令牌（headless + `Network.setUserAgentOverride` 四项同批对齐，实测 4.0 s / 9 条 cookie）；池内按失效标记轮换；Cookie 过期后重新预热。
  - 禁止：代理或出口 IP 轮换（用户已多次明确否决——「不能开启代理访问 Ozon」「直连，不要代理」「不需要俄罗斯出口 ip」，此约束优先于任何吞吐考虑）；伪造跨账号身份；对同一已失效身份无限重试。
  - 区别在于：换的是**同一个真实身份池里的一枚过期票据**，而不是制造一个新身份。
- 历史 `stock_max` 是页面**最大可购数量代理**，未验证等于仓储真实库存。使用 `stock_proxy_raw`／`stock_proxy_value` 等中性字段，保留来源和采集时间，不据此直接计算销量。
- 现有模拟端到端测试不等于真实 PostgreSQL / Redis / ClickHouse / MinIO 或 Ozon 的生产验收。现有 Redis 限速代码也未通过全部真实并发验证。
- 使用真实 Ozon 在线接口的前提：本仓库已实测可通的 Cookie 供给方案（4.4）就位；速率与并发以预检阶段确定的源级预算为准，不采用 `ozon-crawler-local` 的常数；预算尚未核实时，先按保守值（单票据 90 次、单实例 10 并发 9 页/秒）起步，不因此阻断实验。

## 3. 建设方案对比与选择

- 方案 A：保留整套旧工程直接压测。速度快，但已有绕过限制逻辑、旧字段断言和监控缺口，**不选**。
- **方案 B（已选）：在现有仓库建 V2 分支，冻结旧版；保留纯解析器与已有基础设施，单独做可观测测试运行器，拿到证据再开发正式 Worker。** 降低改动风险，可逐模块切换。
- 方案 C：新建仓库、整体重写。隔离彻底但重复开发多、迁移成本高，**不选**。

## 4. V2 第一阶段范围

### 4.1 模块与边界
1. **Buyer Test Adapter**：分开处理 `buyer_inventory` 与 `buyer_reviews`；统一接收批次任务与合规测试源，输出标准化观测及分类错误。默认 Mock / 离线输入；在线连接器由 `CookieSupply` 注入会话，自身不实现预热、不实现代理切换。Cookie 的获取、复用、失效标记与补池全部收敛在供给门（见 4.4），适配器只消费。
2. **12h Benchmark Runner**：可指定运行时长（默认 12h）、接口与批次、预先确认的固定预算、停止策略；支持手动取消、到期停止和意外退出的运行状态记录。**不自动探测/上调**速率或并发。
3. **Metrics & Report**：请求总数/有效记录/批次完成数、P50/P95/P99 响应延迟、成功/有效空包/无效空包、403/429/挑战、超时、每分钟吞吐、CPU/内存、队列等待、写入失败、去重数量；Prometheus 聚合 + 脱敏 JSONL 事件；每 15 分钟摘要和结束报告。
4. **Safety Gate**：数据源级共享固定速率/并发预算、会话状态检查、熔断、人工复核恢复；403、429、401、HTML Challenge 立即熔断**该票据**并从池内取下一枚；不以换代理或换账号绕过，不对同一票据自动重试。3xx 是搜索页的正常跳转（302 → `page_changed=true`），跟随即可，不计入拒绝访问。
5. **Data Quality**：响应 200 不代表成功；区分正常无结果 `empty_valid`、疑似风控空包 `empty_suspect`、解析错误 `parse_failed` 和已写入 `stored`。保留采集快照、schema 版本、原始数据 hash，缺失/未知表示 NULL。
6. **结果存储**：复用已有 PG 元数据与现有对象存储路径；单次测试运行、分段摘要和告警持久化。库存按 `sku + source + region + observed_at` 保留有来源的原始观测；评论若有源 review_id，按 `source + sku + review_id` 去重，无唯一标识时只标记疑似重复。对评价正文和图片按授权、隐私及保留期进行最小化存储。ClickHouse 历史层在真实写入链路验收后再启用，第一阶段不新增数据库产品。

### 4.2 12 小时实验设计
- 预检：本地 Mock / 离线样本完整通过，检查令牌泄露防护、告警接收人、存储容量、采集字段、时钟同步和监控有效性；Cookie 供给门先做连续 20 次 mint 冒烟；源级预算由操作者填入，空缺时用保守起步值（单实例 10 并发、单票据 90 次）并标 `estimated`，不使用 `ozon-crawler-local` 的旧数字。
- 运行：库存与评论作为独立实验/源政策；先一个进程做低速受控验证；在预算不变的情况下运行 12h，持续采集每 15 分钟摘要。只经明确人工批准后进行新的并行实验。
- 停止：到达 12h；人工取消；出现会话连续失效（池内 3 枚票据均被拒）、持续挑战、429/403、超预算；监控或关键持久化失效，均安全停机并保留证据。业务有效的空结果不自动当成封禁，也不直接当作成功。
- 报告：每个源分别展示有效 SKU/评论条数、请求成功率、有效数据率、P95/P99、稳定每小时吞吐、CPU/内存、存储增长、异常分布、完整性/去重结果、停止原因；给出 5 Worker 所需容量的估算区间和不确定性，**不把 1 Worker 结果线性外推当成保证**。

### 4.3 验收与失败判定
- Mock、异常注入和 1 Worker 受控预检测试通过；覆盖重复执行、429/403/Challenge、200 空包、超时、写入失败、停止恢复与敏感信息脱敏。
- 连续 12h 日志完整且运行结果可复核；不发生超预算调用、明文 Cookie 泄漏、无法解释的数据缺失/重复或未报警的中途停止。
- 输出一份清晰区分 `observed`、`estimated`、`unknown` 的报告；**不以跑满 12h 代表库存值准确**。
- 若供给门跑不通、实际数据库或告警尚未准备好，标为 `blocked` 而不是伪造成功；预算未知时用保守起步值并在报告里标 `estimated`，不作为阻断理由。

**4.4.1 为什么必须换内核（本轮最重要的修正）**

Chromium 无论 headless / headful / incognito / 指纹伪装，结果**完全一致**：cookie 0、无 `abt_data`、页内 API 403，落点都是俄语错误页 `Похоже, нет соединения`。这个「五组对照全同」本身就说明检测点在引擎层，而不在 UA 层——改 UA、platform、Client Hints 都没动到被检测的那个变量。

Camoufox 直启（不额外伪装，UA 就是 `X11; Linux x86_64; rv:158.0`）一次通过。原因不是它伪装得更好，而是它**本来就是真 Firefox**：canvas / audio / 字体 / WebGL 全是真实渲染结果。检测的是「是不是真浏览器」，不是「伪装得像不像」。

由此作废：`cdp_warmup` 的裸 Chromium + `Network.setUserAgentOverride` 四项同批路线、`ozon_cookie/profiles.py` 的机型池伪装、以及 headful/xvfb 对照方案。它们建立在错误归因上。

**4.4.2 两条硬约束**

1. **必须直连**。Camoufox 默认继承 `HTTP_PROXY`/`HTTPS_PROXY`（本沙箱 `HIJACK_PROXY_ENABLE=1` 会强制注入），走出去后单请求 1.0 s → 2.1 s、吞吐 9 页/秒 → 0.48 页/秒。launch 必须传 `firefox_user_prefs={"network.proxy.type": 0, "network.proxy.http": "", "network.proxy.ssl": "", "network.proxy.no_proxies_on": "*"}`，并在进程内清空 proxy 环境变量；`proxy={"server": "direct://"}` 不可用（Firefox 报 `NS_ERROR_UNKNOWN_PROXY_HOST`）。
2. **cookie 可以外带，但必须原样传 `Cookie` 头**。这是本轮最容易踩错的一处：
   - 把 9 条 cookie 用 `cookies=dict` 全部塞进请求 → **403**，响应体是带 `challengeURL` 的 incident（`{"incidentId": "fab_chlg_...", "challengeURL": "https://www.ozon.ru/challenge.html?..."}`）。
   - 原样照抄浏览器实发的 `cookie` 头（约 1371 字符，只含 `__Secure-ETC` + `abt_data`）→ **200 / 160 KB**。
   - 原因：浏览器在 API 请求上只带该 path 下的 2 条 cookie，`__Secure-access-token` / `__Secure-refresh-token` / `__Secure-user-id` / `xcid` 等不在这个请求上出现。多带即被判定为会话异常。
   - 正确做法：以 `headers={"cookie": <浏览器实发原串>}` 传入，**不要**用 `cookies=` 参数让库重组；同时照抄 `accept` / `accept-language` / `referer` / `x-o3-app-name` / `x-o3-app-version` / `x-o3-manifest-version` 等全部实发头。TLS 用 `impersonate="firefox147"`（curl_cffi 最高档位）足够，不必精确复刻 158 的 JA3。

**职责边界**

1. 冷启动：Playwright 直启 Camoufox 二进制——不经 `camoufox` python 包封装，该包启动时强制调用 GitHub API 校验 release，限流时直接拒绝启动。过挑战后导出 cookie。
2. 标记失效：下游收到 `403` + `ozon-antibot` 时上报，该 token 转 dead，不重置使用计数、不自动复活。
3. 补池：可用数低于水位线时后台预热补足。前台只租不造，永远不等待预热完成。
4. 403 归因：本次实测证明 403 是**票据级**——同 IP 换新 cookie 立刻恢复，因此不需要「等 100 s 冷却」这一步。403 即熔断当前票据、取池内下一枚；**连续 3 枚被拒**才升级为 IP 层怀疑并停源。
5. 泄漏防护：日志与报告只记 `cookie_id` 与长度，绝不落原始 cookie 值。

**经济账（决定 Worker 数量的关键）**

HTTP 通道实测 60 并发 = 33 页/秒，票据额度至少 419 次未触顶。按保守值（票据 400 页）推算：

- 一枚票据可支撑 `400 / 33 ≈ 12` 秒
- 每秒需要 `33 / 400 ≈ 0.083` 枚新 cookie
- 单次预热 5.5 s，串行一个预热门产能 `1/5.5 ≈ 0.18` 枚/秒
- 结论：**一个串行预热门够用（0.18 > 0.083），余量一倍以上**。预热门是 Camoufox（780 MB/实例），采集侧是 curl_cffi（几乎不占内存），两者解耦

扩展时按实例算：三台采集 Worker 各 60 并发合计 99 页/秒需要 0.25 枚/秒 → 两个预热门刚好。**加 Worker 前先加预热门**。

**票据额度上限尚未测到。** 420 次未触顶，说明 HTTP 通道下的额度远高于页内 fetch 观察到的 90 次——后者很可能是 Firefox 单实例连接数（6 条/域）造成的假象，而非 Ozon 的票据限额。12h 实验要把这个上限打出来，它决定池水位线。

**单票据 90 次这个数必须由 12h 实验复核。** 它决定池水位线，水位线决定预热通道数量，是整条链的根参数。本次只验证了「90–100 次 + 速率阈值」这个量级，长时间低速率下的累积额度未测。

## 5. 有意不做

- 不重写所有爬虫，不追求更强的挑战对抗（Camoufox 已验证可通，够用即停），不测试击穿风控的极限请求率。
- 第一阶段不发布正式 5 Worker 集群，不开发 P6/P7/P8 后台，也不引入 Crawlab/DSH 自动决策链。
- 不自动采购、改价、投广告；不把购物车上限当真实实物库存；不把一次基准测试当成长期容量保证。

**冲突裁决：**
1. 前台库存观测路径与请求实现：优先复核 `ozon-seller-kit/ozon_buyer/collector.py`、`ozon_buyer/http.py`、`ozon_buyer/detail.py`、`docs/BUYER-COLLECTION-METHODS.md` 中与目标页型匹配的路径，再用获准、脱敏原始响应 golden fixture 做一致性测试。Kit 内部实现互相冲突时也**不能臆断**。
2. 库存业务语义：以 Kit 较新的 `docs/field-dictionary.md` 为准；`stock_max` 只是最大可购量代理，不是核实过的物理库存；不根据差值产生“真实销量”。
3. 限速：以 Kit 的实测证据为起始参考（单票据约 90 次、单实例 10 并发 9 页/秒、仅浏览器页内 fetch），不采用 `ozon-crawler-local` 的参数；12h 实验的目的正是把这三个数核准，实验结束前它们标 `estimated`，不是许可上限。
4. 请求路径：实际请求以 Kit 的已验证页型与获准的独立测试样本为准；仅在受控离线合同测试通过后允许对应新 Transport；`ozon-crawler-local` 文档中的不同端点先列“待裁决”，不自动 fallback 到其他路径。
5. 故障语义：参考 `ozon-crawler-local` 的 ok/eof/soft_limit/blocked 分类，但限速、库存含义、端点不采信其断言；Cookie 获取与池内轮换以本仓库实测方案为准（4.4），代理行为一律不采用。连续 3 枚票据仍被拒时停源，记录脱敏证据。

**设计验收新增：** 发布前必须有 `docs/superpowers/evidence/buyer-source-matrix.md`，逐个列出库存、评论的 Kit 源文件/函数、请求页型、字段路径、限速证据、冲突项、已批准参数及测试样本 hash。没有真实数据/授权时只能展示“未验证”，不得声称达到了 12h 在线吞吐。

## 10. 12 小时测试必备日志、限速与字段验收契约（2026-11-09 补充）

### 10.1 审计日志：少而必要，优先可追溯

- 每次 HTTP 请求必须生成**一条终态事件**（包括超时、取消、解析错误、限速拒绝），结构化 JSONL 且只允许白名单键：`ts_utc`、`run_id`、`source_id`、`endpoint_id`、`batch_id`、`request_id`、`attempt`、`status_code`、`outcome`、`duration_ms`、`permit_wait_ms`、`response_bytes`、`observed_records`、`accepted_records`、`schema_version`、`validation_error_codes`、`raw_sha256`（仅获准保存时）、`write_status`、`reason_code`。
- 每 15 分钟保存聚合指标：发出/拒绝/完成请求数、实际 rps、峰值并发、有效 SKU/评论条数、唯一项、空包/错误分类、P50/P95/P99、延迟趋势、CPU/内存、日志/数据库大小和源状态；结束时可复核原始事件与摘要计数。
- **分层留存（建议默认，可被更严格的授权政策缩短）**：脱敏请求事件 30 天、15 分钟聚合 180 天、最小化样本 7 天；原始响应正文默认**不保留**，仅获明确许可后加密存入受限对象存储并设置到期清理。日志按日期/大小轮转，禁提交到 Git。
- 不记录 Cookie、Authorization、原始 URL 查询字符串、IP/账号、评论作者、评论正文、图片和敏感异常堆栈；如事件无法持久化，标记 `failed` 并停止测试，不得继续无证据请求。

### 10.2 源级限速契约

- **库存、评论独立政策**：确认数据源、页面/端点、`max_rps`、`burst`、`max_concurrency`、`min_interval_seconds`、单次 `max_requests` 与 24 小时 `max_requests_per_day`，含政策生效时间与证据来源。数值未定时用保守起步值（单实例 10 并发、单票据 90 次、仅浏览器页内 fetch），报告里标 `estimated` —— 12h 实验的目的正是把这三个数核准，不是等外部签发。
- 每次请求发出前，必须原子检查预算 + 到期时刻 + 并发许可；记录 `permit_wait_ms` 和 `rejected_reason`。本轮单进程用严格本地计数与令牌桶；未来多 Worker 切换共享 Redis 许可，但**不得**按 Worker 单独放大限额。
- 收到 401/403/429、访问挑战时熔断**该票据**并从池内取下一枚；不换代理、不换账号、不对同一票据重试、不提高速率。连续 3 枚票据被拒则暂停该源。跳类目页是排名抖动的正常表现，不作为拒绝处理。5xx 等暂态错误只在既定重试预算和限速总账范围内处理。监控/日志/存储异常触发失败停止。
- `ozon-crawler-local` 的请求速率及端点不可用于生产配置；Kit 的实测数字是起点，由 12h 实验核准后固化为正式政策。

### 10.3 字段验证契约

- **库存**：`sku` 保存为字符串、明确页型和观测时间。库存落**两个并列字段**：`stock_proxy_max_items`（tile 的 `maxItems`，平台单次可购上限）与 `stock_text_remaining`（文案「N ед осталось」的真值）。`maxItems` 超过 2000 会封顶，此时两支都要保留并标 `capped=true`——只存 `maxItems` 会在爆款上得到恒定 2000 的假数列。两者缺失均为 `NULL`，0 与 `NULL` 分开；非整数、负值、来源 widget 缺失、目标 SKU 未出现在页面分别标异常，不得伪造库存 0。
- **评论**：`sku`、观察时间、评分（若存在须 1–5）、来源页面和评论标识来源；`review_id` 缺失时不随意用作者+正文造唯一键，按疑似重复处理；正文/图片的留存要单独许可。
- 每一批记录 `expected_count`、`parsed_count`、`valid_count`、`rejected_count`、`unknown_count`、`schema_version` 和字段缺失率；HTTP 200 + 空 widget/格式变化为 `empty_suspect` 或 `invalid`，不得伪装成功。字段映射变更必须先更新经 Kit 来源矩阵验证的 fixture 与回归测试。
- 强制用 Kit 的库存/评论实现与**合法脱敏 golden**复核，而不是采用 crawler-local 里的未经裁决端点、库存字段或限速数据。

### 10.4 附加验收

离线测试必须覆盖：日志字段脱敏、每请求终态事件数对账、聚合计数与请求日志一致、日志写入失败熔断、独立接口限额/跨任务共享预算、预算耗尽拒绝、全局节流、库存 0/NULL/封顶、评论 1–5 星与重复、字段漂移、200 静默空包。线上 12h 测试须满足三条：供给门通过连续 20 次 mint 冒烟、源级预算已填、可一键停止。
