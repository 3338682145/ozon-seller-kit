# Ozon V2 前台采集监控与 12 小时基准测试设计（草案）

> 状态：待用户审核；**本文件不是实施授权**。日期：2026-11-09。
> 现有主分支基线：`05884b6538eddce211b38df71ff26fbee874402b`；归档分支：`archive/pre-v2-2026-11-09`。
> 本设计仅限第一阶段；正式 5 Worker、后台 P6/P7/P8、分析面板和试销决策模型分别设计。

## 1. 意图与业务背景

用户已有 Ozon Buyer/Seller 采集 Demo；后续需支持类目→关键词→SKU→利润研究，以及库存/评论的日度跟踪。目标是最终让同一服务器上的 5 个 Worker 共享队列运行，每日可处理约 100 万条 SKU 库存观测（待性能验证）。当前**先不设计 Worker 最终并发量**，先对买家前台库存代理字段与评论接口做合规、低风险、可重复的 12 小时稳定性测试，得到真实吞吐、数据质量与资源成本依据；后台接口留到下一阶段。

## 2. 已有代码与现实约束

- 可复用：`ozon_buyer/` 的纯解析函数、`collector/adapters/base.py` 的适配器契约、`collector/rate_limit/distributed.py`、`collector/errors.py`、`collector/api.py` 的指标与监控入口，及既有 Prometheus/Grafana 配置。
- **不能直接生产复用**：`collector/adapters/buyer_snapshot.py` 当前仅允许离线快照；旧 Buyer 网络代码含 CDP Cookie 预热、挑战处理、浏览器指纹模拟与 403 补池策略，不得通过新监控层继续沿用这些规避限制的行为。
- 历史 `stock_max` 是页面**最大可购数量代理**，未验证等于仓储真实库存。使用 `stock_proxy_raw`／`stock_proxy_value` 等中性字段，保留来源和采集时间，不据此直接计算销量。
- 现有模拟端到端测试不等于真实 PostgreSQL / Redis / ClickHouse / MinIO 或 Ozon 的生产验收。现有 Redis 限速代码也未通过全部真实并发验证。
- 使用真实 Ozon 在线接口的先决条件：确认合法授权范围、接口条款及**每接口**请求速率、并发和每日预算；未知时只能 Mock/获准保留的离线原始快照。

## 3. 建设方案对比与选择

- 方案 A：保留整套旧工程直接压测。速度快，但已有绕过限制逻辑、旧字段断言和监控缺口，**不选**。
- **方案 B（已选）：在现有仓库建 V2 分支，冻结旧版；保留纯解析器与已有基础设施，单独做可观测测试运行器，拿到证据再开发正式 Worker。** 降低改动风险，可逐模块切换。
- 方案 C：新建仓库、整体重写。隔离彻底但重复开发多、迁移成本高，**不选**。

## 4. V2 第一阶段范围

### 4.1 模块与边界
1. **Buyer Test Adapter**：分开处理 `buyer_inventory` 与 `buyer_reviews`；统一接收批次任务与合规测试源，输出标准化观测及分类错误。默认 Mock / 离线输入；在线连接器仅在授权且通过配置门禁后启用，不提供挑战求解、身份轮换、自动 Cookie mint、自动代理切换。
2. **12h Benchmark Runner**：可指定运行时长（默认 12h）、接口与批次、预先确认的固定预算、停止策略；支持手动取消、到期停止和意外退出的运行状态记录。**不自动探测/上调**速率或并发。
3. **Metrics & Report**：请求总数/有效记录/批次完成数、P50/P95/P99 响应延迟、成功/有效空包/无效空包、403/429/挑战、超时、每分钟吞吐、CPU/内存、队列等待、写入失败、去重数量；Prometheus 聚合 + 脱敏 JSONL 事件；每 15 分钟摘要和结束报告。
4. **Safety Gate**：数据源级共享固定速率/并发预算、授权与许可检查、熔断、人工复核恢复；403、429、3xx、401、HTML Challenge 或其他拒绝访问迹象立即暂停对应源，不以换账号/代理/Cookie 或自动重试来绕过。
5. **Data Quality**：响应 200 不代表成功；区分正常无结果 `empty_valid`、疑似风控空包 `empty_suspect`、解析错误 `parse_failed` 和已写入 `stored`。保留采集快照、schema 版本、原始数据 hash，缺失/未知表示 NULL。
6. **结果存储**：复用已有 PG 元数据与现有对象存储路径；单次测试运行、分段摘要和告警持久化。库存按 `sku + source + region + observed_at` 保留有来源的原始观测；评论若有源 review_id，按 `source + sku + review_id` 去重，无唯一标识时只标记疑似重复。对评价正文和图片按授权、隐私及保留期进行最小化存储。ClickHouse 历史层在真实写入链路验收后再启用，第一阶段不新增数据库产品。

### 4.2 12 小时实验设计
- 预检：本地 Mock / 许可离线样本完整通过，检查令牌泄露防护、告警接收人、存储容量、采集字段、时钟同步和监控有效性；真实在线参数由操作者填入**已确认**的源级预算，不使用仓库 README 的旧吞吐数字。
- 运行：库存与评论作为独立实验/源政策；先一个进程做低速受控验证；在不改变授权限额的情况下运行固定预算 12h，持续采集每 15 分钟摘要。只经明确人工批准后进行新的并行实验。
- 停止：到达 12h；人工取消；出现权限失效/风控挑战/429/403/许可超标；监控或关键持久化失效，均安全停机并保留证据。出现业务有效的空结果不自动当成封禁，也不直接当作成功。
- 报告：每个源分别展示有效 SKU/评论条数、请求成功率、有效数据率、P95/P99、稳定每小时吞吐、CPU/内存、存储增长、异常分布、完整性/去重结果、停止原因；给出 5 Worker 所需容量的估算区间和不确定性，**不把 1 Worker 结果线性外推当成保证**。

### 4.3 验收与失败判定
- Mock、异常注入和 1 Worker 受控预检测试通过；覆盖重复执行、429/403/Challenge、200 空包、超时、写入失败、停止恢复与敏感信息脱敏。
- 连续 12h 日志完整且运行结果可复核；不发生超授权调用、明文 Cookie 泄漏、无法解释的数据缺失/重复或未报警的中途停止。
- 输出一份清晰区分 `observed`、`estimated`、`unknown` 的报告；**不以跑满 12h 代表库存值准确**。
- 若限额未知、真实访问不获许可、实际数据库/告警尚未准备好，标为 `blocked` 而不是伪造成功或启动真实在线压测。

## 5. 有意不做

- 不重写所有爬虫，不改旧脚本去实现更强挑战处理，不测试绕过风控的极限请求率。
- 第一阶段不发布正式 5 Worker 集群，不开发 P6/P7/P8 后台，也不引入 Crawlab/DSH 自动决策链。
- 不自动采购、改价、投广告；不把购物车上限当真实实物库存；不把一次基准测试当成长期容量保证。

## 6. 后续阶段（不属于本次交付）

1. 基于测试结果确定批次规模、Redis Streams/Pg Outbox 的 5 Worker 共享源级配额、lease、checkpoint、DLQ 与错误恢复。
2. 建库存/评论长期快照、关键词 P7/P8 与 SKU P6 关联数据层，补齐字段契约和时间窗口。
3. 建类目机会识别、竞争强度、采购价与利润情景、60 天试销现金回收/库存规划，再接采集与分析双面板。
4. 后台真实源需独立合规和限额门禁，届时另出设计与实施计划。

## 7. 待确认、由实施人员不得擅自推定

- 买家库存/评论的实际授权请求上限、最大并发、每日预算、账号权限，以及是否允许保存原始评论/图片；
- 用于前台的真实在线访问实现是否具备合规授权替代渠道；**不能直接把旧反挑战实现视为合规**；
- 本地服务器的 CPU、内存、磁盘与告警收件人；如未提供，配置项保留空值并阻止正式在线实验；
- 将来取得准确库存字段后再更新数据契约与分析模型，不能在本次用现有 `stock_max` 替代。
